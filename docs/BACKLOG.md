## B1. Маршрут: киллы за час до старта слежения не попадают в отчёт

**Симптом.** `за /route A B` (и `/route_status`) показывает якобы чистые гейты, хотя за час
до старта слежения на маршрутных системах были кемпы — при ручной проверке сторонним
гейтчеком киллы видны.

**Требование.** Модуль мониторинга — ответственный: молчаливое «проглатывание» ошибок zK
недопустимо, пользователь обязан видеть, что данные неполные, а не «чисто».

**Что уже известно (факты из кода и журнала прода):**
1. `RouteMonitor.snapshot()` возвращает `ok` (получены ли данные по всем системам), но
   `handlers.cmd_route` этот результат **игнорирует** — сообщение старта строится из
   `watch.events` как есть.
2. В `RouteMonitor._tick_watch` сбой запроса zK (`kills is None`) превращается в `kills = []`:
   система выглядит «чистой», в журнал уходит только `WARNING … zK <sid>: TimeoutError`,
   счётчик `stat_errors` растёт. То же в `ZoneMonitor.live_snapshot()`.
3. В журнале прода такие таймауты идут сериями: 2026-09-25 16:40:32 … 16:43:39 — шесть
   подряд по разным системам (то есть один тик может дать «чистый» отчёт по половине маршрута).
4. `/route_status` тоже не отображает неполноту данных.

**Гипотезы (проверять по порядку):**
- **H1 (главная):** тихие сбои zK — «не кемпят» выводится при неполных данных.
- **H2:** семантика окна/локации: мы считаем только киллы, чей `zkb.locationID` ∈ itemID гейтов
  системы (решение D4), а сторонний гейтчек может считать все киллы системы (станции и т.п.)
  или другое окно — расхождение ожидаемое, нужно сверить на конкретной системе и часе.
- **H3:** ограничения zK API: `fetch_system_kills` не пагинирует (лимит 200 киллов на страницу),
  окно `pastSeconds/3600`, задержка публикации киллов.

**План диагностики и правки:**
1. Использовать возвращаемый `ok`: в старте маршрута, `/route_status` и зональном
   live-опросе писать «данные не получены по N системам из M» вместо молчаливого «чисто»;
   ретраи с бэкоффом на сбоях zK; счётчики сбоев последнего тика — в `/ping`.
2. Сравнительная валидация на реальных данных: взять систему и час, где сторонний гейтчек
   показывал кемп, и вручную запросить `zK /solarSystemID/<id>/pastSeconds/3600/`, сопоставив
   киллы и `locationID` с нашим фильтром гейтов.
3. Проверить пагинацию на «густых» системах (>200 киллов за час — например, Amamake в пик).

**Критерий готовности:** на одной и той же системе/часе наш отчёт совпадает с ручной
валидацией по zK, а при недоступности zK пользователь явно видит неполноту данных.

## B2. Пороги и кулдаун не сохраняются («Хранилище недоступно»)

**Симптом.** `/settings_cooldown 20м` (и, по-видимому, любые другие `/settings_*`) отвечает
«Хранилище недоступно — пороги не сохраняются.» — настроить бота под себя невозможно.

**Что уже известно (факты):**
1. Такая строка есть только в одной ветке: `storage is None` (в проде-ревизии `4ef1f20` —
   `handlers.py:379`; в текущем коде — расширенная проверка `storage.available` + `LazyStorage.ensure()`,
   добавленная хотфиксом v0.10.1).
2. На 2026-09-29 прод работал на `4ef1f20` (= `origin/main`), то есть **без** хотфикса `04b02c2`
   (LazyStorage) и без v0.11.x: локально было +4 незапушенных коммита → фикс на прод не попал.
3. В журнале прода с 11.09 **нет** строки `SQLite недоступен (…)` — единственного пути к
   `storage is None`; значит на текущем запуске хранилище инициализировалось. Диск: 38% занято
   (5.2 ГБ свободно); `data/` принадлежит `gatecheck`; миграции 001/002 применены.
4. `/ping` (только админ) уже показывает состояние БД: «Хранилище: ок / НЕДОСТУПЕН (ошибка)».

**План:** 1) выкатить текущий `main` (`python scripts/deploy.py`, см. `deploy/README.md`);
2) воспроизвести `/settings_cooldown 20м` — если снова «недоступно», выводить в ответ текст
исключения (сейчас он скрыт) и смотреть `/ping`; 3) проверить права/локи/WAL у
`data/gatecheck.sqlite3`; 4) добавить тест восстановления LazyStorage и лог-алерт, если
хранилище недоступно дольше N минут.

**Критерий готовности:** пороги и кулдаун применяются, видны в `/settings` и переживают рестарт.

## B3. Фича: мгновенное подтверждение приёма запроса + редактирование ответа

**Зачем.** Команды с длинной обработкой (`/route A B` — первый опрос всех систем маршрута,
`/zone_on` и `/zone_status` без подписки — живой опрос зоны, кнопка «🔄 Гейты: обновить»)
молчат несколько секунд: пользователь думает, что бот завис. Нужно подтверждение за ≤0.5 с,
которое затем **редактируется** в готовый ответ.

**Как делать (aiogram 3):**
1. Сразу после команды: `placeholder = await message.answer("⏳ Запрос принят, собираю данные…")`.
2. По готовности: `await placeholder.edit_text(final_text, reply_markup=..., disable_web_page_preview=True)`.

**Краевые случаи, которые обязательно учесть:**
- лимит 4096 символов (старт маршрута на 15+ систем может превысить) → фолбэк: отправить
  новое сообщение, а плейсхолдер либо удалить, либо превратить в «продолжение ниже»;
- `TelegramBadRequest: message is not modified` — игнорировать;
- лимиты Telegram: правки ≈1/с на чат (20/мин) → прогресс не чаще раза в секунду;
- при провале правки — отправить новое сообщение, ответ не терять;
- единый хелпер (например, `progress_message()` в `handlers.py`), чтобы не дублировать логику
  в `/route`, `/zone_on`, `/zone_status` и в кнопке обновления;
- опционально: показывать прогресс («проверено N/M систем») на длинных опросах зоны/маршрута.

**Критерий готовности:** на `/route Amamake Jita` подтверждение появляется < 1 с, финальный
ответ приходит тем же сообщением (как сейчас), при любой ошибке пользователь всё равно
получает ответ.
