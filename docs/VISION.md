# Gatecheck Bot — идеология проекта

> Версия: **0.2** · Дата: 2026-09-08 · Статус: основные решения зафиксированы (интервью v1 проведено), часть вопросов — на верификацию спайком M0
>
> Этот документ — первоисточник замысла проекта. Решения из интервью перечислены в §5.1 (D1–D9); неподтверждённое помечено «ОТКРЫТЫЙ ВОПРОС (OQ-N)» — сводка в §11.

## 1. Кратко (elevator pitch)

Telegram-бот для пилотов EVE Online, которые зарабатывают на сборе обломков после гейт-кампов (сальваг/лоот). Бот следит за киллами у гейтов в выбранной зоне фарма и пушит уведомления, когда активность растёт — значит, скоро будет что собирать и можно логиниться. Два режима: фоновый мониторинг зоны фарма (неспешный, раз в 3–5 минут) и усиленный мониторинг маршрута следования (опрос каждые 40–60 секунд, предупреждения о каждом новом килле на воротах по пути).

## 2. Проблема

На популярных lowsec-системах (фарм-зоны, PVP-хабы) у гейтов регулярно происходят замесы. После них на поле остаются обломки с лутом. Сальваг-фармер логинится альтом (Ноктис и т.п.) и собирает добро — но только когда бой закончился и мишка ушла. Сейчас это делается вручную: вкладка зКилла, периодические проверки глазами, «гейтчек» в чатах. Это медленно и легко пропустить окно возможности — трупы собирают за минуты.

Нужен инструмент, который сам говорит: «в системе X на воротах за последний час N киллов, активность растёт — пора».

## 3. Цели и нецели

### Цели (в скоупе v1)

- **G1 — Мониторинг зоны фарма.** Подписка вкл/выкл на зону. Первая зона — пресет «Hed + примыкающие системы» (см. 6.1). Фоновый опрос раз в 3–5 минут, обновление состояния систем, пуши при значимых событиях (семантика — D5).
- **G2 — Маршрут с усиленным мониторингом.** Команда «кратчайший маршрут A→B»: бот строит маршрут по графу гейтов, показывает системы и включает активный мониторинг с опросом каждые 40–60 секунд. Алерт при росте числа киллов на воротах по пути хотя бы на 1 (семантика — D5, группировка подов — OQ-4).
- **G3 — Работа 24/7 на слабом VPS (Debian 13)**: минимальный CPU/RAM, состояние переживает рестарт, аккуратные ретраи/бэкофф ко всем внешним API.
- **G4 — Публичный репозиторий на GitHub**: секреты вне репо, документация, этикетные User-Agent.

### Нецели (вне скоупа v1)

- Ингейм-интеграция и ESI-аутентификация персонажей.
- Интел локал-чата (детект клоаков — требует игрового клиента/парсинга логов; отдельная тема).
- Веб-интерфейс/дашборд.
- Маршруты через wormhole-соединения и Pochven-триггеры: считаем только классические гейты (статичный граф).
- Оценка содержимого/ценности обломков (потенциально позже через zkb totalValue).
- Автопостинг в сторонние каналы — только личные уведомления подписчикам.

## 4. Глоссарий

| Термин | Значение |
|---|---|
| Гейт (stargate) | Межсистемные ворота; уникальный itemID + координаты в системе |
| Килл на воротах | Killmail, чья позиция жертвы близка к позиции гейта (порог — OQ-3) |
| Зона фарма | Набор систем, за которыми следит подписчик (v1: единый пресет — D7) |
| Базлайн | Фоновый уровень киллов системы; нужен, чтобы отличать «обычную жизнь» от всплеска |
| Окно (window) | Скользящий интервал, в котором считаем киллы (окна алертов — D5: 10 мин и 1 ч) |
| Активный режим | Мониторинг конкретного маршрута: опрос 40–60 с, алерты на новые киллы на воротах по пути |
| TTL маршрута | Время жизни активного мониторинга маршрута (D6: 1 час), после — автоотключение |
| RedisQ | Реалтайм-поток киллов от zKillboard (long-poll) |
| ESI | Официальное API CCP (статика вселенной: системы, гейты, имена) |

## 5. Пользовательские сценарии

### Сценарий A — «Фарм-зона» (фоновый мониторинг)

1. Пользователь включает мониторинг зоны: `/zone on` (v1 — единый пресет, D7).
2. Бот раз в 3–5 минут обновляет состояние систем зоны: киллы на воротах каждой системы за окно.
3. Пуши только «интересных событий» (D5): всплеск ≥3/10 мин, накопление ≥8/час, droppable ISK выше порога. Формат: система, счётчики, ссылка на zKillboard.
4. `/zone off` — выключение. `/zone status` — состояние зоны по запросу.

### Сценарий B — «Маршрут» (активный мониторинг)

1. Пользователь: `/route Amamake Rens` (система-отправление, система-назначение).
2. Бот строит кратчайший маршрут по графу гейтов (BFS), отвечает списком систем с текущими счётчиками киллов на воротах каждой.
3. На TTL **1 час** (D6) включается активный мониторинг: опрос систем маршрута каждые 40–60 с.
4. При ≥1 новом килле на воротах любой системы маршрута — мгновенный пуш (система, сколько за окно, ссылка). Анти-спам: дедупликация по killID; вопрос группировки ship+pod — OQ-4.
5. `/route stop` — погасить активный маршрут досрочно. Активный маршрут один на пользователя (D6).

## 5.1 Решения, зафиксированные в интервью

- **D1 (аудитория).** Бот **полностью публичный**: любой может `/start` и подписаться; на каждого — разумные лимиты (кол-во зон/маршрутов, частота пушей). Защита от абьюза обязательна.
- **D2 (стек).** **Python 3.13 + aiogram 3 + SQLite + asyncio**, один процесс. Развёртывание с учётом слабого VPS (Debian 13).
- **D3 (источник данных).** Гибрид: **RedisQ** — реалтайм-поток для активного мониторинга маршрутов; **zK API** — история/базлайн зоны; автоматический fallback на polling, если RedisQ недоступен с VPS. Проверка доступности RedisQ — спайк в начале M1.
- **D4 (атрибуция «на воротах»).** Ориентируемся на резолв киллборды (zK `locationID`); локальная геометрия (позиция жертвы vs координаты гейтов из SDE) — предмет спайка и резервный механизм.
- **D5 (алерты зоны).** Сводок нет вообще — только «интересные события». Триггеры (пороги настраиваемы, дефолты):
  - **всплеск**: ≥3 килла на воротах системы за последние **10 минут**;
  - **накопление**: ≥8 киллов на воротах системы за последний **час**;
  - **ценность**: сумма **droppable ISK** за 10 минут > настраиваемого порога — даже один дорогой килл повод провериться;
  - cooldown на повторные алерты по одной системе.
  - Ресёрч: поля zkb для droppable (`droppedValue`? либо items `quantity_dropped` × цены ESI/Fuzzwork).
- **D6 (жизненный цикл маршрута).** Один активный маршрут на пользователя, **TTL 1 час** с авто-гашением; TTL явно указывается пользователю при включении мониторинга. Общий принцип: бот при настройках всегда сообщает пользователю о действующих ограничениях (TTL, лимиты, частоты).


## 6. Ресёрч источников данных (факты, проверены 2026-09-08)

### 6.1 География зоны

- Констелляция **Hed**: id **20000372**, регион **Heimatar** (id 10000030), lowsec. Системы:
  - Amamake — 30002537 · Vard — 30002538 · Siseide — 30002539
  - Lantorn — 30002540 · Dal — 30002541 · Auga — 30002542
- ⚠️ Исправление первичного предположения: Hed находится **не в Delve** (Delve = регион 10000060). Amamake — классическая lowsec PVP/фарм-система, что идеально согласуется с идеей проекта.
- «Примыкающие системы» = системы соседних констелляций, соединённые гейтами с системами Hed. Вычисляются по графу гейтов; итоговый пресет зоны фиксируется в конфиге (D7).

### 6.2 zKillboard API (по официальным докам zkillboard.com/api/)

- `GET https://zkillboard.com/api/{modifiers}/` — killmails в ESI-формате + zkb-метаданные. До **200 киллов на страницу**, страницы 1–100, newest-first.
- Модификаторы (комбинируются, entity-фильтр первым):
  - `solarSystemID/{id}` (алиас `systemID`), `constellationID/{id}`, `regionID/{id}`
  - **`locationID/{id}`** — фильтр по «resolved location» (кандидат на прямой фильтр «килл на воротах», требует верификации, OQ-3)
  - `killID/{id}`, `warID/{id}`, флаги `highsec/lowsec/nullsec/w-space`, `solo/ganked`
  - `pastSeconds/{sec}` — до **604 800** (7 суток), шаг 1 час; `year/{YYYY}/month/{M}`; `page/{n}`
- Отключены (legacy): `orderDirection`, `startTime/endTime`, `beforeKillID/afterKillID`, `limit`, `zkbOnly`, `no-attackers`, `no-items`, `asc/desc`, `json/xml`, списки через запятую.
- Этикет (обязательно): осмысленный **User-Agent** с URL/контактом проекта, **gzip**, кэширование у нас, паузы между запросами, trailing slash в путях. Публикуемых жёстких лимитов в доках нет — держим скромный темп и бэкофф на 403/429.
- Пример целевого запроса: `/api/solarSystemID/30002537/pastSeconds/3600/` (+ `page/`, если >200).

### 6.3 RedisQ (реалтайм-поток zKillboard) — ТРЕБУЕТ ПРОВЕРКИ

- Схема: `GET https://redisq.zkillboard.com/listen.php?ttw=2` — long-poll до ttw секунд; ответ `{"package": {...}}` или `{"package": null}`. В package — полный killmail (включая `victim.position`) + zkb (`locationID`, `hash`, `totalValue`, `npc`, `solo`…). Параметр `packageID` — подтверждение доставки, чтобы не терять пакеты.
- Плюс: один поток на весь мир → локальная фильтрация, почти реалтайм, нет гонки за лимитами запросов.
- ⚠️ Из песочницы разработки хост не резолвится (сетевые ограничения среды). **Проверить доступность с ПК/VPS в спайке M1.** Если недоступен — fallback: polling zK API (6.2) с частотой по режиму. Решение D3 — гибрид с fallback.

### 6.4 ESI (официальное API CCP) — статика

- `/universe/systems/{id}/` — включает `stargates` (itemID + destination) → собираем полный граф гейтов.
- `/universe/constellations/{id}/` — список систем констелляции; `/universe/names/` — пакетный резолвинг ID→имя (до 1000 за запрос); `/search/` — поиск систем по имени.
- Маршруты считаем **локально** (BFS/Dijkstra по графу) — внешние роутеры не нужны. Статика почти не меняется: кэш на диск, обновление раз в сутки / по команде админа.
- Альтернатива статике: SDE-дампы EVE Ref (everef.net) — там же координаты гейтов для геометрической проверки (6.6).

### 6.5 Сторонние гейтчек-сервисы

- **eve-gatecheck.space (EVE Gatecamp Check)** — эталонный сервис, референс метрик:
  - Легенда порогов: `0` / `≤2` / `≥3` **киллов у гейтов системы за прошедший час**; отдельные маркеры для smartbomb-киллов и применения hic/dictor'ов у гейтов.
  - Проверка маршрута «from → to» с режимами Shortest/Secure/Unsecure и списком исключений.
  - **Публичного API нет** (`/api` → 404), премиум-функции (gatecamp finder «киллы у гейтов по всему EVE») монетизируются (25m ISK/мес). **Парсить не будем** — хрупко и неэтично; строим свою трубу данных (6.2–6.4). Их пороги и метрики берём как ориентир для дефолтов.
- `gatecamp.watch` — сторонний агрегатор гейт-кампов; из песочницы не проверен (DNS). Кандидат «на посмотреть» (OQ-9).

### 6.6 Атрибуция «килл на воротах» — ключевая развилка (решение D4)

- **Вариант A**: резолв киллборды — zK `locationID` (если zK привязывает килл к itemID гейта). Ноль своей геометрии.
- **Вариант B**: локальная геометрия: `victim.position` из killmail + координаты гейтов из SDE/ESI → килл «на воротах», если дистанция ≤ порога.
- **Вариант C**: килл «в системе» без привязки к воротам (грубо, шумно).
- **D4**: ориентируемся на **A** (верим резолву киллборды), **B — предмет спайка** и резерв, если A ведёт себя недостоверно. Верификация поведения `locationID` на реальных данных — обязательная часть спайка M1.

## 7. Архитектура (черновик v0.1)

Один asyncio-процесс Python 3.13; состояние в SQLite; HTTP — aiohttp (gzip, свой User-Agent, бэкофф, jitter).

```
 Telegram ◄──пуши──► aiogram3 (long polling)  ◄── /команды
                        │
                 Ядро мониторинга (окна, пороги, dedup killID, cooldown)
                   │                    │
        RedisQ-listener (реалтайм)   zK API-poller (базлайн зоны / fallback)
                   │                    │
                   ▼                    ▼
              dedup по killID ──► SQLite (киллы, подписки, маршруты, состояние)
                   ▲
        Статика: граф гейтов + координаты (ESI/SDE → json-кэш на диске, обновление раз в сутки)
```

Принципы:

- Пуши только «интересных событий» (D5) и маршрутный режим с порогом ≥1 нового килла.
- Роутер: BFS по статичному графу (миллисекунды, без внешних вызовов).
- Прикидка нагрузки: зона ~15–25 систем при опросе 3–5 мин ≈ 5–8 req/мин к zK — в рамках этикета. Активные маршруты при многих пользователях закрывает RedisQ-поток (один на инстанс бота).
- Telegram: ≤1 msg/s на чат, группировка событий (ship+pod в одном сообщении — OQ-4), HTML parse mode, длины сообщений с запасом.
- SQLite: WAL + busy_timeout; простые .sql-миграции в репо.
- Конфиг: `.env` (BOT_TOKEN, ADMIN_IDS, прокси) + пресеты зон в yaml; `.env` в .gitignore, `.env.example` в репо (репо публичное!).
- Тесты: pytest + моки HTTP; unit-тесты окон/порогов/BFS; GitHub Actions: ruff + pytest.
- Наблюдаемость: структурные логи (journald), счётчики ошибок API, `/ping` для админа.

- **D7 (модель зон).** v1 — **только пресет «Hed + примыкающие системы»** для всех пользователей; код/конфиг сразу проектируем под добавление новых пресетов позже (файл пресетов, без переработки схемы).
- **D8 (деплой).** **GitHub Actions автодеплой**: по пушу в main — лить на VPS по SSH и рестартовать systemd-юнит. Локальная разработка на Win11.
- **D9 (философия продукта).** Это **личный бот автора, доступный другим** — не универсальный инструмент для всех и каждого. Публичность — побочный эффект, а не цель: не гнаться за конфигурируемостью «для всех кейсов»; зоны/пороги/лимиты подобраны под потребности автора и прозрачны для пользователей.

## 8. Модель данных (черновик)

- `users` (chat_id PK, tg_name, is_admin, settings_json, created_at)
- `subscriptions` (id, chat_id FK, zone_id, active, created_at) — зона на чат
- `routes` (id, chat_id FK, origin_id, dest_id, system_ids_json, created_at, expires_at, status) — TTL 1 ч (D6)
- `kill_cache` (kill_id PK, system_id, gate_item_id, kill_time, victim_ship_type_id, victim_alliance_id, total_isk, dropped_isk, raw_json, inserted_at) — чистка старше 7 суток
- `alerts_log` (id, chat_id, kind, system_id, sent_at) — cooldown и отладка
- Статика: файлы `data/graph.json`, `data/gates.json` (+версия/дата обновления в meta)
- Счётчики окон (10 мин / 1 ч) считаем на лету из `kill_cache` — проще и честнее, чем дублировать агрегаты.

### Командный интерфейс (черновик)

- `/start`, `/help` — онбординг + описание ограничений (D6)
- `/zone on|off|status` — фоновый мониторинг зоны (v1 — пресет, D7)
- `/route <A> <B>` / `/route stop` — активный мониторинг маршрута
- `/settings` — пороги (всплеск/час/ISK), cooldown (в пределах разрешённых границ)
- `/ping` — админ: живость, статистика API, версия статики

## 9. Ограничения, риски и меры

| Риск | Мера |
|---|---|
| zK API недоступен / 403-429 за агрессивный опрос | Скромные темпы (5–8 req/мин на зону), кэш, бэкофф с jitter, деградация с честным сообщением пользователю |
| RedisQ недоступен с VPS | Fallback на polling (D3); переключение автоматическое, логируется |
| `locationID` не резолвится в гейты надёжно | Спайк M1 (OQ-2); резерв — геометрия по `victim.position` + координаты гейтов (D4) |
| Абьюз публичного бота | Fair-use лимиты на чат (кол-во зон/маршрутов/пушей), cooldown, админ-бан; все лимиты прозрачны (D6, D9) |
| Спам Telegram (>1 msg/s на чат) | Очередь отправки с rate-limiter, группировка одновременных событий |
| Секреты в публичном репо | `.env` в .gitignore, `.env.example` без секретов, токен только на VPS/локально |
| Слабый VPS | Один процесс, без тяжёлых зависимостей, память ≤ ~150–200 МБ, `Restart=always`, SQLite вместо сервера БД |
| Изменения внешних API (zK/ESI/RedisQ) | Спайк-заметки, тесты структуры ответов, версии статики, аккуратные ошибки в логах |
| «Забытые» подписки/маршруты грузят API | TTL маршрутов (D6), автоочистка, лимиты |
| Прокси/блокировки из сети VPS | Реализовано: `PROXY_URL` + **автономный прокси-пул** (v0.3.0, самодостаточен при блокировках); проверка доступности всех эндпоинтов в спайке M0 |
